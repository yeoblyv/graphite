# Internationalization

Every string the library itself draws — the "Yes"/"No"/"OK"/"Cancel"
buttons in [ShowConfirm, ShowMessage, ShowTextEditor](modals.md), the
column headers and filter labels in [ShowFilePicker](modals.md#showfilepicker-browse-and-select-a-file),
and the prompt/error text in [ShowValueEditor](fader.md#showvalueeditor-typing-an-exact-value)
— is resolved through `Application.T` at the point each dialog is built,
against whatever `Locale` the `Application` currently has set.

This is not a library-only mechanism. `Locale`, `Catalog`, and `T` are the
same tool a program uses to translate 100% of its own UI — window titles,
labels, button text, status messages — into any language: see
[Translating your own application](#translating-your-own-application)
below. One `Application`, one `Locale`, one `T`, resolving both the
library's strings and yours through the same per-locale dictionary.

## `Locale` and `Application.T`

```go
type Locale string

func (app *Application) Locale() Locale
func (app *Application) SetLocale(l Locale)
func (app *Application) T(key string, args ...any) string
```

A new `Application` starts at `Graphite.LocaleEnglish`. `SetLocale` changes
it going forward — like `SetTheme`, it doesn't retroactively touch
anything already on screen; a `Show*` dialog picks up the new locale the
next time it opens.

```go
app := Graphite.NewApplication()
app.SetLocale(Graphite.LocaleUkrainian)

Graphite.ShowConfirm(app, "Видалити", "Видалити цей файл?", Graphite.BtnDanger, func() {
	os.Remove(path)
})
// buttons read "Так" / "Ні"
```

`T` is also how you resolve one of the library's translation keys
yourself, e.g. to build a custom modal (see
[modals.md](modals.md#building-your-own-modal)) that matches the current
locale:

```go
mod.AddWidget(Graphite.NewButton(2, 5, app.T(Graphite.KeyCancel), Graphite.BtnDefault, func() {
	app.CloseModal()
}))
```

A key with no translation anywhere falls back to English, then to the key
string itself — `T` never returns an empty string, so a missing or
misspelled key degrades to something readable and debuggable instead of a
blank button.

`args`, when given, are applied with `fmt.Sprintf` after the key is
resolved — this is how `ShowValueEditor`'s prompt ("Value (%g-%g):")
works in every language without each one needing its own formatting code.

## Built-in locales

The library ships a complete, prepared `Catalog` — every key below
translated — for:

| `Locale` constant | Language |
|---|---|
| `LocaleEnglish` | English (default) |
| `LocaleUkrainian` | Ukrainian |
| `LocaleRussian` | Russian |
| `LocaleGerman` | German |
| `LocaleFrench` | French |
| `LocaleSpanish` | Spanish |
| `LocalePortuguese` | Portuguese |
| `LocaleItalian` | Italian |
| `LocalePolish` | Polish |
| `LocaleDutch` | Dutch |
| `LocaleTurkish` | Turkish |
| `LocaleCzech` | Czech |
| `LocaleJapanese` | Japanese |
| `LocaleChinese` | Chinese (simplified) |
| `LocaleKorean` | Korean |

`Locale` is a plain string, not a closed type — these constants exist for
convenience and typo safety, but `SetLocale` (and `SetTranslations` below)
accept any value.

## Adding or overriding a language

```go
type Catalog map[string]string

func (app *Application) SetTranslations(locale Locale, catalog Catalog)
```

`SetTranslations` merges `catalog` into the dictionary `T` looks up first
for `locale`, ahead of the library's own prepared `Catalog` for that
locale (if any) and ahead of the English fallback. A key `catalog`
defines overrides whatever was registered for it before — including one of
the library's own built-in keys; every other key registered earlier for
`locale` is kept. Calling it again doesn't start over, so a dictionary can
be built up incrementally across as many calls as convenient. Two uses:

**A language the library doesn't ship**, using its own `Locale` value and
every key:

```go
app.SetLocale(Graphite.Locale("eo")) // Esperanto
app.SetTranslations(Graphite.Locale("eo"), Graphite.Catalog{
	Graphite.KeyYes:    "Jes",
	Graphite.KeyNo:     "Ne",
	Graphite.KeyOK:     "Bone",
	Graphite.KeyCancel: "Nuligi",
	// ... the remaining keys, see below
})
```

A key you don't include still resolves — first to English, so a partial
catalog is always safe to ship while the rest of a translation is in
progress.

**Overriding a couple of strings** in a language the library already
provides — you only need to include the keys you're changing, since every
other key you haven't touched still resolves to the built-in `Catalog`:

```go
app.SetTranslations(Graphite.LocaleEnglish, Graphite.Catalog{
	Graphite.KeyOK: "Confirm", // house style: "Confirm" instead of "OK"
})
```

## Translating your own application

Give your own UI text a key the same way the library's own code does, and
resolve it with `T`:

```go
app.SetTranslations(Graphite.LocaleEnglish, Graphite.Catalog{
	"myapp.window.title": "My Application",
	"myapp.toolbar.save": "Save",
	"myapp.status.count":  "%d item(s) selected",
})
app.SetTranslations(Graphite.LocaleUkrainian, Graphite.Catalog{
	"myapp.window.title": "Моя програма",
	"myapp.toolbar.save": "Зберегти",
	"myapp.status.count":  "Вибрано: %d",
})

win := Graphite.NewWindow(60, 20, " "+app.T("myapp.window.title")+" ")
win.AddWidget(Graphite.NewButton(2, 2, app.T("myapp.toolbar.save"), Graphite.BtnSuccess, save))
app.SetStatus(app.T("myapp.status.count", len(selected)))
```

Any string works as a key. Namespace your own — `"<yourapp>.<area>.<element>"`,
as above — so they can never collide with the library's own `graphite.*`
keys (see [Translation keys](#translation-keys)), and so two modules of a
larger program can't collide with each other either. There's no separate
"application catalog" object: your keys and the library's live in the same
per-`Locale` dictionary, resolved by the same `T`, falling back through the
same English-then-key-itself rule described above — so a missing
translation in your own UI degrades exactly as gracefully as a missing one
in a `Show*` dialog would.

### Recommended layout: a `locales` package

For anything past a handful of strings, put translations in their own
package instead of inline `Catalog` literals scattered through UI code —
one file per language, e.g.:

```text
locales/
├── locales.go   // package locales; re-exports nothing, just groups the files below
├── en.go        // var English = Graphite.Catalog{ ... }
├── uk.go        // var Ukrainian = Graphite.Catalog{ ... }
└── de.go        // var German = Graphite.Catalog{ ... }
```

```go
// locales/en.go
package locales

import "github.com/yeoblyv/graphite"

var English = Graphite.Catalog{
	"myapp.window.title": "My Application",
	"myapp.toolbar.save": "Save",
	"myapp.status.count": "%d item(s) selected",
}
```

```go
// main.go
import "myapp/locales"

app.SetTranslations(Graphite.LocaleEnglish, locales.English)
app.SetTranslations(Graphite.LocaleUkrainian, locales.Ukrainian)
app.SetTranslations(Graphite.LocaleGerman, locales.German)
```

This is deliberately a plain Go source file, not a data file `LoadCatalog`-style
loading would read at runtime — for a compiled, cross-platform binary like
this library targets ([layout.md](layout.md), the portability rules in the
project's own engineering standard), a translation baked in at compile time
beats one that has to be shipped and found on disk next to the binary:

- **The compiler checks it.** A duplicate key inside one `Catalog{...}`
  literal is a `go build` error, not a silently-last-write-wins runtime
  surprise; a typo in a variable name (`locales.Frnech`) fails the build
  instead of shipping a language that silently never applies.
- **Nothing to ship or lose.** The translation compiles straight into the
  binary alongside everything else — no separate file to package, deploy,
  or have go missing/corrupted/wrong-encoding on a user's machine at
  runtime.
- **Cross-compilation is free.** `make build-all`/`build.ps1` already
  cross-compile the whole program per target OS ([README.md](../README.md#building));
  a `locales` package rides along with zero extra step, unlike a runtime
  file whose path handling would itself need the cross-platform care
  [layout.md](layout.md) and the project's own portability rules require.

### Composing several `Catalog` values with `Merge`

```go
func (c Catalog) Merge(others ...Catalog) Catalog
```

`Merge` returns a new `Catalog` with each of `others` applied on top of `c`
in order — a key repeated in a later one wins, the same override-on-top-of-
a-base rule `SetTranslations` itself follows — without modifying `c` or any
of `others`. This is the native-Go equivalent of "including" a shared base
file: split a large language across a common part and several per-screen
parts, then combine them with an ordinary function call the compiler
checks like any other:

```go
// locales/common.go
package locales

var CommonEN = Graphite.Catalog{"myapp.ok": "OK", "myapp.cancel": "Cancel"}

// locales/settings_screen.go
var SettingsEN = Graphite.Catalog{"myapp.settings.title": "Settings"}

// main.go
app.SetTranslations(Graphite.LocaleEnglish, locales.CommonEN.Merge(locales.SettingsEN))
```

Or skip `Merge` entirely and just call `SetTranslations` once per part —
it already merges into whatever was registered for that `Locale` before
(see [Adding or overriding a language](#adding-or-overriding-a-language)
above), so `Merge` is a convenience for building one `Catalog` to pass in
a single call, not the only way to compose translations.

## Translation keys

Every key below is defined as an exported constant (`Graphite.KeyYes`,
`Graphite.KeyOK`, ...) so a custom `Catalog` can reference it without
retyping the raw string.

| Key | English text | Used by |
|---|---|---|
| `KeyYes` | `Yes` | `ShowConfirm` |
| `KeyNo` | `No` | `ShowConfirm` |
| `KeyOK` | `OK` | `ShowMessage`, `ShowTextEditor`, `ShowValueEditor` |
| `KeyCancel` | `Cancel` | `ShowTextEditor`, `ShowValueEditor`, `ShowFilePicker` |
| `KeyValueRequired` | `Value cannot be empty.` | `ShowTextEditor` |
| `KeyOpen` | `Open` | `ShowFilePicker` (title and button) |
| `KeyDirLabel` | `Dir: ` | `ShowFilePicker` (path field prefix) |
| `KeyFileNameLabel` | `File name: ` | `ShowFilePicker` |
| `KeyColumnName` | `Name` | `ShowFilePicker` (listing header) |
| `KeyColumnDate` | `Date Modified` | `ShowFilePicker` (listing header) |
| `KeyColumnType` | `Type` | `ShowFilePicker` (listing header) |
| `KeyColumnSize` | `Size` | `ShowFilePicker` (listing header) |
| `KeyFileFolder` | `File folder` | `ShowFilePicker` (folder rows) |
| `KeyFileGeneric` | `File` | `ShowFilePicker` (extensionless file rows) |
| `KeyFilterAll` | `All Files (*.*)` | `ShowFilePicker` (filter dropdown) |
| `KeyFilterGph` | `GPH Files (*.gph)` | `ShowFilePicker` (filter dropdown) |
| `KeyFilterImage` | `Image Files (*.jpg, *.png, *.jpeg)` | `ShowFilePicker` (filter dropdown) |
| `KeyFilterVideo` | `Video Files (*.mp4, *.avi, *.mkv)` | `ShowFilePicker` (filter dropdown) |
| `KeyValuePrompt` | `Value (%g-%g):` | `ShowValueEditor` |
| `KeyValueRangeError` | `Enter a number between %g and %g.` | `ShowValueEditor` |

## What this doesn't cover

- **Layout is fixed-width, not RTL-aware.** The prepared catalogs are all
  left-to-right languages. A `Catalog` for a right-to-left language (e.g.
  Arabic, Hebrew) works for word-level translation, but Graphite doesn't
  reflow or mirror widget layout, so a caller supplying one is responsible
  for whatever layout adjustments their program needs.
- **Wide glyphs still cost the terminal columns they occupy.** CJK
  translations render correctly (see [layout.md](layout.md) and
  `width.go`'s rune-width handling), but a fixed-width field (e.g.
  `ShowFilePicker`'s date column) truncates with an ellipsis rather than
  growing, exactly as an overlong English string would.
- **No locale auto-detection.** `SetLocale` is always explicit — the
  library doesn't read `$LANG`/`$LC_ALL` or an OS locale API for you, so a
  program that wants to match the user's system language reads it itself
  and passes the result to `SetLocale`.
- **No runtime file loading.** Translations are Go values (`Catalog`
  literals), compiled into the binary — see
  [Recommended layout: a locales package](#recommended-layout-a-locales-package)
  above for why. If a project's translations already live in another
  format (`.po`, a spreadsheet export, a CAT-tool's JSON/YAML export,
  ...), generate the `locales` package's `.go` files from it as a build
  step, the same way any other generated Go source is handled — Graphite
  itself has no opinion on where a `Catalog` literal's content originally
  came from.
